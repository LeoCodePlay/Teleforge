# 为什么本仓的缓存命中率上不了 99%:一条自加的"每请求折叠"把前缀缓存了一遍遍作废

审计对象:本仓(`F:\Dm\companyProject\自己\远程ssh工具`,teleforge)
参照基准:`E:\RJ\DmRJ\deepseek-harness`(dsh)

## 0. 结论

命中率低的**唯一**结构性原因,是本仓在**每次请求**前对历史做了一遍"保留最近 N 条大工具结果"的
折叠(`AGENT.TOOL_RESULT_PRUNE.ABS_FLOOR_*`,dsh 里**没有**这个机制)。它的折叠点是**滑动窗口的函数**:
窗口每前进一格,就有一条**历史中段**的消息被改写;提供方前缀缓存从第一个变化的字节起失效,
于是该点之后的整段缓存全部作废。实测每个会话里会发生**几十次**这样的改写,单次作废
**2 万~30 万 token**,把长会话命中率从 ~99.2-99.4%(只追加时的上限)拖到 **96~98.6%**。

修法就是"照搬 dsh 的对话处理逻辑":**删掉这条每请求触发路径**,让裁剪只在压缩水位/爆窗合格后
随压缩一起发生,并且**判定只取决于消息内容**(纯函数、无位置窗口),于是模型可见面只能向后追加。

## 2. 根因:每请求重算的滑动窗口折叠

修复前 `server/agent/agent.ts` 每次请求前:

```ts
const P = AGENT.TOOL_RESULT_PRUNE;                       // ABS_FLOOR_*
if (P.ABS_FLOOR_TOKENS > 0 && measureEnvelope(...).total > P.ABS_FLOOR_TOKENS) {
  const r = pruneToolResults(historyMsgs, {
    keepRecent: P.ABS_FLOOR_KEEP_RESULTS,                // 4
    keepRecentChars: P.ABS_FLOOR_KEEP_CHARS,             // 16000
    minChars: P.ABS_FLOOR_THRESHOLD_CHARS,               // 2000
    minSaveChars: P.ABS_FLOOR_MIN_SAVE_CHARS             // 8000
  });
  historyMsgs = r.messages;                              // ← 模型可见面被中途改写
}
```

参数含义:`超过 2000 字符的工具结果`里,只留"最近最多 4 条 / 16000 字符",其余折叠成头尾摘要。
问题在于**"最近"是按位置算的**:

- 窗口只统计"超过 2000 字符的结果",中间那些小结果、以及模型的长回复都不算;
  所以窗口边界**在 token 距离上可以离请求末尾几万 token**(实测折叠点之后 25k~236k token);
- 每次新结果进来,窗口前进一格 → **又有一条旧消息从"原样"变成"已折叠"**;
- 加上 `minSaveChars` 攒批门槛,窗口一次会跳好几格,单次作废的尾部更大;
- 该路径从"预估请求 > 60k token"起**每步都跑**,于是长会话里反复失血。

同一次改动留下的自证:`agent.ts` 当时的日志会打印
`历史工具结果折叠:N 条…作废缓存尾部 ~20452 token`——一边省几百~几千字符,一边作废两万多 token。
在缓存命中输入价约为未命中 1/10(以 DeepSeek 官方价目为例)的前提下,这笔账是净亏。

## 4. 剩下的损耗(不是本仓能修的)

- **提供方缓存驱逐 / 网关 LRU**:请求体只差尾巴却只命中前一段(如命中 323584 / 输入 517688),
  且下一步又能满命中 —— 典型的"中间某个 64-token 块被挤掉"。
- **换 Key 后缓存不共享**:`s_muwvzfc3rkea5z` 的 `seq1635` 记录「API Key 余额不足,已切换到
  第 2/3 个可用 Key」,紧接着的 `t9/s1` 只命中 62.5%(掉 192896 token)。多 Key 轮询本身是
  可用性策略,但把它放在会话中途,代价就是整段前缀缓存。
- **压缩检查点**:`/compact`、水位自动压缩都会换掉一段前缀(一次性,量级 = 被换掉那段之后的全部)。
  这是 dsh 也有的必要代价。
- 量级上,这三类加起来在每个会话里约 **0.3-0.8 个百分点**;把 §2 那条路径删掉后,
  长会话的**可达区间是 99.0%-99.4%**(= 只追加上限 − 上述不可控部分)。

## 6. 同类残余风险(未改)

`trimMessagesByBudget(historyMsgs, resolveCharBudget(ctxWindow))`(窗口×2 字符预算)同样是
"每请求在投影层改前缀",而且它改的是**第 0 条消息**(系统+工具之后立刻分叉),一次触发就作废
整段历史缓存。它只在历史超过"窗口×2 字符"时触发:当前用户模型声明 1M 窗口(预算 2M 字符),
实测会话最高 60 万 token 未触及。若要彻底消除这一类风险,应把它也改成**一次性检查点**
(落一条 drop 检查点事件,让后续投影从该点起跳),而不是每次请求重新裁剪。
